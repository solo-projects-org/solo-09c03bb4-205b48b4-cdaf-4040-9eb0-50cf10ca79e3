# 电表检定台 · 放行判定

逐个编号判定电表检定结论的网页系统。上传检定报告（报告号 + 首末编号 + 不合格名单
CSV），放行人员在网页按号段查询：每个编号以**覆盖它且未撤回的报告中号码最大者**为准。

## 规则

| 事项 | 行为 |
| --- | --- |
| 判定 | 覆盖该编号、未撤回、`report_no` 最大的报告；在该报告名单内为**不合格**，否则**合格** |
| 无报告覆盖 | **待检** |
| 上传顺序 | 任意乱序，结论只取决于报告号，与上传先后无关 |
| 首末编号 | 含两端 |
| 名单为空 | 整段合格 |
| 同号同内容重传 | 不新增、不修改，保持原状态（含“已撤回”与勘误） |
| 同号异文重传 | 整份拒收，HTTP 409，原报告不受影响 |
| 撤回 | 软删除，按剩余报告重判；可重复撤回；全部撤回后为待检 |
| 号段规模 | 百万级编号不逐号展开：入库仅一条报告行，查询按“结论 + 依据报告”分段 |
| 数据一致性 | 一次查询在单个 SQLite 读事务内完成，结论与依据来自同一次提交 |
| 重启 | 全部状态在 SQLite 文件中，重启后查询结果不变 |

### 勘误（每份报告一次）

报告号（表号）整段录错时，在报告详情页填写**原号段内待改的首末号**和**正确起号**：

- 该段及其中的不合格编号按原顺序整体移到等长的新号段：
  段内编号 `s` 变为 `s - 待改首号 + 正确起号`，不合格判定随之平移。
- 新号段可以与**被移动段自身**重叠（例如 `5000–5010 → 4995–5005`），
  但必须在 `0 … MAX_SERIAL` 内，且不能占用**本报告未移动的编号**。
  其他报告的号段不是保留区：报告本就允许重叠，号大者优先，勘误后的新段照常参与判定。
- 原上传号段与不合格名单**原样保留**；详情页同时显示勘误前后的号段、当前生效覆盖和原名单。
- 被移走的原号段不再由本报告覆盖，其中的编号按其余报告重判（可能变待检、合格或不合格）。
- 每份报告只办一次勘误。同参数重试返回原勘误（不重复写入，撤回后重试亦然）；
  改参数返回 409。
- 已撤回的报告拒绝**首次**勘误；撤回使已勘误报告整份失效（勘误记录保留）；
  重传原件（同号同内容）保留勘误与撤回状态。
- 勘误在单个写事务中完成，任一步失败则整份回滚，重启后仍按最后一次已提交状态判定。
- 覆盖范围按**区间**存储（`report_coverage`），百万号段的勘误只是增删几行区间。

## 启动

```bash
docker compose up --build
# 打开 http://localhost:8000/
```

数据库落在命名卷 `meter-data`（容器内 `/data/meter.db`），`docker compose down`
不会删除；需要清空时用 `docker compose down -v`。

本地不用 Docker 时：

```bash
python3 -m pip install -r requirements.txt
PM_DB_PATH=data/meter.db python3 -m uvicorn app.main:app --port 8000
```

## 页面

- `/reports`：上传报告、报告台账（含勘误标记）、撤回
- `/reports/{no}`：报告详情，展示原号段、勘误前后号段、当前生效覆盖、勘误后名单与原名单，
  并在未勘误且未撤回时提供勘误表单
- `/query`：放行查询，输入首末编号，按结论 + 依据报告分段查看
- `/api/query?serial_first=&serial_last=`：同一结果的 JSON
- `/api/reports`、`/api/reports/{no}`：报告台账；详情含 `coverage`、`correction`、
  `failures`（生效）与 `original_failures`（原上传）
- `/healthz`：健康检查（容器 healthcheck 使用）

### 上传字段

- **报告号**：按检定先后递增的正整数；上传可以乱序。
- **起始编号 / 结束编号**：含两端。
- **不合格名单 CSV**：每行一个编号，或用逗号/空白分隔；可有 `编号`/`serial` 表头；
  留空文件或不选文件表示整段合格。编码支持 UTF-8（含 BOM）与 GB18030。
  名单内任何编号落在号段之外，整份拒收。
  示例见 `examples/failures.csv`。

## 查询输出

- **统计**：号段内合格 / 不合格 / 待检的**完整**编号数。
- **按结论与依据汇总**：每种（结论, 依据报告）组合覆盖多少编号，始终覆盖整个号段。
- **分段明细**：连续且结论、依据报告相同的编号合并为一段。为防超大响应，明细最多
  `max_segments` 段（默认 20000，表单可调）；超出时只列前面连续的一段并明确提示，
  此时统计与汇总仍是全量。
- **依据报告快照**：本次判定实际用到的报告及范围、名单条数、接收时间。

（含重叠、撤回、乱序）逐号比对；`tests/test_erratum.py` 另用同样的逐号模型随机生成

## 设计要点

- 编号区间在内部统一用半开区间 `[lo, hi)`，`last + 1` 溢出风险由 `MAX_SERIAL`
  限制规避。
- 报告上传的号段与名单不可变；判定读 `report_coverage`（生效覆盖，可多段）与
  `failed_serials`（生效名单）。勘误只改写这两张派生表，同时把原名单归入
  `original_failed_serials` 并写入 `report_corrections`（`report_id` 唯一，天然限一次）。
  旧库启动时按 `reports.serial_first/last` 回填一次覆盖，已有勘误的库不受影响。
- 写入用 `BEGIN IMMEDIATE`（单写者），读取用快照事务；SQLite 为 WAL 模式。
- `failed_serials` 主键 `(report_id, serial)` 天然去重；报告表 `failed_count`
  让“无不合格”的报告查询时免于访问明细表。
- 查询按区间边界扫描并用大顶堆取当前覆盖报告中号码最大者；每个区间再按名单切分，
  因此工作量为 O(边界数 + 命中名单数)，与号段跨度无关。
  实测 2000 份相互重叠的报告、10,000,001 个编号的号段，单次查询约 47 ms，
  均为 633 段；把明细上限压到 100 段时统计仍与全量一致。
- 统计口径（合格/不合格/待检）按区间用 `COUNT(*)` 精确累加，**始终覆盖整个号段**；
  只有“分段明细”列表受 `max_segments` 限制。放行判定应以统计与汇总为准。
- 重传一致性用整份内容的 SHA-256：报告号、首末编号、排序去重后的名单共同决定，
  因此 CSV 行序、重复行、空行、表头都不影响“同内容”的判断；勘误不改变指纹。
- 报告详情页 `/reports/{no}` 列出生效名单（最多 500 条）、勘误前的原名单（最多 500 条）
  与内容指纹，便于核对。

## 未完成 / 后续

- 无鉴权：谁能打开页面谁就能上传、勘误和撤回。生产部署前应加登录与角色
  （上传员 / 放行人），并限制勘误权限。
- 勘误不能撤销或再次修改：发现填错只能靠撤回整份报告（本需求即“每份报告只办一次”）。
  如业务需要更正勘误，应另加审批与作废流程。
- CSV 只做逐行/分隔符解析，不是完整 CSV 解析器（带引号字段、内嵌换行不支持）。
- 明细段数上限目前是单次响应的保护；如需导出全量分段，应改为分页或流式下载。
- 未做审计日志（谁在何时上传/勘误/撤回）。时间已记录，操作人未记录。
- 单机 SQLite，适合单实例；多副本部署需换成服务端数据库或单写者服务。
